# Theodore Nelson CV Review and Application Strategy

## Recruiter scorecard: original CV

| Measure | Score | Direct assessment |
|---|---:|---|
| First impression | 6/10 | Clean and credible, but the opening sounds tentative and does not immediately distinguish you from other graduates. |
| ATS compatibility | 7/10 | Selectable text and standard content, but logos, long links, mixed positioning, and less conventional labels such as "Selected Project Proof" reduce clarity. |
| Technical credibility | 7/10 | The stack and project set are strong evidence. Credibility is weakened by repeated words such as "practice" and by missing repository links, tests, architecture notes, and measurable outcomes. |
| Junior developer attractiveness | 7/10 | You show initiative and broad exposure, but the original CV buries the strongest advantage: mature support experience plus software-building ability. |
| Interview potential | 6/10 | Good raw material, but too much generic wording and too little prioritisation. A recruiter could miss your strongest projects during a short scan. |

## Recommended section order

### Junior developer applications

1. Name, target title, and contact links
2. Professional summary
3. Technical skills
4. Selected technical projects
5. Development experience
6. Earlier IT support experience
7. Education and certifications

### Software support applications

1. Name, target title, and contact links
2. Professional summary
3. Support and technical skills
4. Professional support experience
5. Relevant software projects
6. Education and certifications

## Top 10 improvements made

1. Reframed you from an inexperienced graduate into a junior developer with 10 years of transferable technical-support maturity.
2. Replaced tentative phrases such as "practice," "seeking to learn," and "help build" with evidence of systems built, deployed, packaged, and supported.
3. Put technical projects before older employment in the developer version so recruiters see current coding evidence first.
4. Created a separate support-engineer narrative instead of forcing one CV to target two different hiring profiles.
5. Rewrote project bullets around business problems, technical decisions, delivered workflows, and reviewable outcomes.
6. Added high-value ATS terms naturally, including REST APIs, JPA, JDBC, RBAC, relational modelling, incident triage, issue reproduction, and deployment troubleshooting.
7. Consolidated the 2012-2022 support history in the developer CV while retaining full detail in the support CV.
8. Removed logos and complex visual structure from print documents to improve parsing, scan speed, and professional consistency.
9. Used standard ATS headings: Professional Summary, Technical Skills, Projects, Experience, and Education.
10. Kept every claim defensible and avoided invented percentages, ticket volumes, user counts, or performance figures.

## Keywords to tailor by vacancy

### Java and backend roles

Java, Spring Boot, Spring Framework, REST API, JPA, Hibernate, JDBC, Maven, object-oriented programming, MVC, SQL, PostgreSQL, MySQL, unit testing, JUnit, debugging, Git, GitHub, CI/CD, authentication, authorization, RBAC, CRUD, microservices, Agile, SDLC.

### Web and full-stack roles

JavaScript, HTML5, CSS3, React, Next.js, responsive design, frontend development, backend development, RESTful services, JSON, API integration, form validation, accessibility, Git, deployment, Vercel, Render.

### Software support roles

Application support, technical support, incident management, incident triage, troubleshooting, root-cause analysis, issue reproduction, log analysis, SQL queries, database support, API troubleshooting, SLA, ticketing system, escalation, knowledge base, user training, remote support, production support, monitoring.

Only add keywords that you can explain in an interview. In particular, add Hibernate, Maven, JUnit, CI/CD, Agile, ticketing platforms, SLA, log analysis, or monitoring tools only after confirming actual experience.

## Missing information to add

- Employment months, office locations, and whether each role was permanent, contract, internship, or learnership.
- Quantified support scope: approximate users, sites, devices, tickets per week, resolution rate, SLA performance, or major incidents handled.
- Direct GitHub repository links for the three featured projects, not only installer downloads.
- Testing evidence: JUnit, integration tests, API tests, Postman collections, or documented manual test cases.
- Build and engineering tools actually used, such as Maven or Gradle, Docker, GitHub Actions, IDEs, and Linux.
- Ticketing, remote support, directory, and enterprise tools used in technician roles, such as ServiceNow, Jira, Active Directory, Microsoft 365, SCCM, Intune, or TeamViewer.
- Project dates, your exact ownership, whether any were client projects, and whether other contributors were involved.
- Outcomes from real users or clients: time saved, records managed, workflows replaced, adoption, feedback, or reliability improvements.
- Qualification wording exactly as printed on each certificate, including awarding body and completion date.
- Work authorisation, driver's licence, languages, notice period, and willingness to relocate or travel when relevant to the vacancy.

## Why this positioning works

Recruiters usually scan title, summary, skills, latest evidence, and dates before reading details. The revised versions make your target role explicit, place proof close to the top, and show a coherent career story: an experienced support technician deliberately adding formal development training and practical software delivery. That story is stronger and more credible than presenting yourself as a typical graduate with no professional technology background.

Use `cv-junior-developer.html` for Java, backend, full-stack, graduate, and internship applications. Use `cv-support-engineer.html` for application support, software support, technical support, junior support engineer, and support-to-development roles. Tailor the headline and first 8-12 skills to each job description before applying.
